    Running a Batch on SLURM¶

    A batch (scenario 'scenario=<glob>', and with --multirun every case of each scenario's sweep) runs its cases one after another, in one process, on one CARLA. On a machine or cluster with SLURM, the same batch can run its cases as the tasks of a SLURM array job instead, several at once, each on a CARLA of its own:

    uv run scenario --multirun 'scenario=cut_in/*' +sweep.odd_sample.count=24 \
  launcher=slurm launcher.array_parallelism=2 launcher.gres=shard:1 launcher.mem=12G

    It is off unless a run selects it. The launcher config group is not part of the default config: a run that does not name it composes the same config as before, and the batch runs here, exactly as it always has. launcher=local says the same explicitly.

    The batch writes what a local batch writes, where a local batch writes it (outputs/<date>/<time>/), under the same names: every case's {Scenario}_result.json, {Scenario}.trajectory.jsonl, coverage, ODD archive, environment and CARLA recording, and batch_results.json with the summary table at the end. A case's outputs do not depend on which task ran it or when.

    How it works¶

    On the machine you run scenario on (a SLURM submit host):

    1. The batch is expanded, labelled, built and statically checked exactly as a local batch is: the ODD sampling, the case labels, the static check (once a config shape), the map fetched. A config error is refused here, before anything is submitted.
    2. A manifest is written into the batch's output directory (slurm/manifest.json): every case's scenario and overrides, its resolved config, and the file stem it is to be named by.
    3. sbatch --array=0-(N-1)%K submits the cases, launcher.cases_per_task to a task, at most launcher.array_parallelism tasks at once.
    4. By default scenario follows the array (squeue, and the outcome each task records) until it ends, then prints the summary and writes batch_results.json, as a local batch does, and exits 0 when every case passed. Ctrl-C cancels the batch's jobs, waits (up to 60 s) for their tasks to leave the queue, and collects. With --no-wait (launcher.wait=false) it submits and exits, and a small job that runs once the array has ended (--dependency=afterany) collects the batch; should that job not be submitted, scenario says so, with the array's job id, and exits non-zero (scenario-slurm wait collects the batch instead).

    Each task, on its node:

    1. takes a slot of ports no other task on the node holds and nothing listens on (Ports);
    2. composes each of its cases' configs from the manifest's scenario and overrides, and refuses to run one that no longer resolves to the config it was submitted with (a job that does not run in the submitting environment);
    3. builds them (not checked again: the submitting process did), starts a CARLA on its ports and runs its cases one after another through the same queue a local batch uses, writing their files into the batch's directory under the names a local batch gives them;
    4. records each case's outcome as soon as it has run (slurm/results/<case>.json), and its own progress in slurm/tasks/<submission>-<task>.json (host, ports, state, peak resident memory); with rerun.enabled=true it also converts each case's trajectory log into its Rerun recording ({stem}.rrd) and records whether that failed, so collect reports the recordings as a local batch does (Seeing a run). The submitting process only checks that the rerun extra is installed; the nodes need it too;
    5. stops its CARLA however it ends: at the end, on scancel, on the signal SLURM sends launcher.signal_grace_seconds before launcher.time runs out, and -- through the job script -- when the worker itself was killed, even by the SIGKILL that ends a scancel after SLURM's KillWait (CARLA runs in a session of its own, which that signal misses): a small watchdog process of its own, started once the slot is taken, stops CARLA when the worker ends without having done so, and keeps the slot locked until then.

    Following, collecting, resubmitting¶

    scenario-slurm takes the batch's output directory:

    scenario-slurm status   outputs/2026-10-18/12-00-00   # cases, jobs, tasks
scenario-slurm wait     outputs/2026-10-18/12-00-00   # follow, then collect
scenario-slurm collect  outputs/2026-10-18/12-00-00   # summary, batch_results.json
scenario-slurm resubmit outputs/2026-10-18/12-00-00   # the cases with no result
scenario-slurm cancel   outputs/2026-10-18/12-00-00   # scancel the batch's jobs

    A case that has no outcome -- its task was cancelled, ran out of time, was killed for memory, or its node failed -- is reported as ERROR with a message saying so, and collect lists them. resubmit submits again the cases with no outcome and those that raised on every attempt (ERROR); --failed adds the ones that ran and failed, --cases a,b names them (labels or indices; a case named twice runs once), and --array-parallelism/--cases-per-task change how they are spread. A case run again replaces its earlier files: before it runs, the task removes every output of its stem (run_outputs), its T4 dataset directory ({stem}.t4) included, so none of the last attempt's is left beside the new result. So resubmit refuses while a job of the batch is queued or running, or while squeue cannot tell whether one is (--force submits all the same). collect can be run any number of times.

    sacct is not needed: the batch is followed through squeue and the files the tasks write.

    The result viewer does the same from its pages: its run panel submits a batch with launcher=slurm, and a SLURM batch's page shows its cases, jobs and tasks as they run and resubmits, collects or cancels it (Running through SLURM).

    Configuration¶

    launcher=slurm selects conf/launcher/slurm.yaml; every key can be set on the command line (launcher.mem=12G), or in a config.

    Key Default
    partition, account, qos null sbatch --partition/--account/--qos
    time null sbatch --time; the task is sent SIGTERM signal_grace_seconds before it runs out
    mem, cpus_per_task, gres null sbatch --mem/--cpus-per-task/--gres (gpu:1, or shard:1 to share a GPU)
    array_parallelism null at most this many tasks at once (--array=...%K); null: no cap
    cases_per_task null cases a task runs on its CARLA; null: the cases spread evenly over array_parallelism tasks (one case a task without a cap)
    job_name null acs-<date>-<time> of the output directory
    extra_sbatch_args [] further sbatch arguments
    export null sbatch --export; null: ALL, or NONE with remote_cwd
    env_passthrough null variables recorded at submission and set again in the job; null: see below, or none with remote_cwd
    setup [] shell lines the job runs before the worker (module load, source .venv/bin/activate)
    env {} variables set in the job, last
    python null the interpreter the jobs run (the tasks and the collect job): an absolute path, a path relative to the job's working directory (.venv/bin/python), ~/... (the home on the node), or a command on the node's PATH (python3); null: the submitting one
    remote_cwd null where the jobs work on the nodes, for a submit host that sees their file system at another path (A submit host with other paths); null: the directory scenario runs in
    headless true unset DISPLAY in the job, so CARLA renders off-screen
    start_stagger_seconds 0 no task of the batch starts sooner than this after another did: the first wave, the tasks started as slots free up, a resubmit's (Shared state)
    wait true follow and collect; false (or --no-wait): submit and exit
    poll_seconds 15 how often wait asks squeue
    cancel_on_interrupt true Ctrl-C while waiting cancels the batch's jobs
    collect_job true with wait: false, a job that collects once the array ends
    collect_mem 2G its --mem
    signal_grace_seconds 120 --signal=B:TERM@N
    port_base, port_slots 20000, 1000 where the tasks' port slots are (Ports); port_slots at least 1
    port_lock_dir null where the slots' locks are; null: /dev/shm/acs-slurm-ports-<uid>, else /tmp (Ports)

    cases_per_task trades a task's start -- CARLA takes about 50 s to start, and a driver policy about as long to load -- against how evenly the cases spread and how many a lost task takes with it.

    The job's environment¶

    A task runs with the Python the batch was submitted from (sys.executable, or launcher.python) and its environment:

    1. sbatch --export=ALL (launcher.export) hands the job the environment of the shell sbatch runs from;
    2. the job script then sets again, as they were when the batch was submitted, the variables launcher.env_passthrough matches: PATH, LD_LIBRARY_PATH, PYTHONPATH, PYTHONHOME, VIRTUAL_ENV, CONDA_PREFIX, CARLA_* (CARLA_EXECUTABLE), AUTOWARE_*, ONEPLANNER_*, TYPESAFE_CARLA_*, GLIBC_TUNABLES, MALLOC_*, CUDA_HOME, CUDA_PATH, CUDAToolkit_ROOT -- so scenario-slurm resubmit from another shell runs the cases as they were submitted;
    3. launcher.setup runs;
    4. launcher.env is set.

    A driver policy's variables belong on env_passthrough (a pattern: launcher.env_passthrough=[...] replaces the list) or in launcher.env. No token or credential is on the default list, and a name with TOKEN, SECRET, KEY, PASSWORD or CREDENTIAL in it (in any case) is not recorded through a pattern (AUTOWARE_*) either -- only when env_passthrough names it exactly, or launcher.env sets it: the manifest and the job scripts holding the values are files in the batch's output directory (both the user's alone, mode 0600 and 0700). With export: NONE, the job has only what steps 2 to 4 give it.

    With launcher.remote_cwd set, none of this comes from the submit host: the job has the environment SLURM gives it on the node (export: NONE), the variables env_passthrough names only when it is given, then setup and env (A submit host with other paths).

    A config that reads the environment (${oc.env:ONEPLANNER_MAP_DIR}) is resolved in the task too; a case whose config resolves differently there than where it was submitted is refused, naming the keys that differ.

    A submit host with other paths¶

    By default the jobs run where scenario was run: the directory it ran in, the interpreter it ran with and the batch's output directory are recorded by their absolute paths, which the nodes must see as the submit host does. A submit host that sees the nodes' file system somewhere else -- a workstation that mounts a node's ~/workspace/OnePlanner with sshfs or NFS at ~/mnt/node/OnePlanner, under another user's home -- names the nodes' paths instead, none of them absolute:

    # On the submit host, in its mount of the node's ~/workspace/OnePlanner:
cd ~/mnt/node/OnePlanner
uv run scenario --multirun 'scenario=cut_in/*' +sweep.odd_sample.count=24 \
  launcher=slurm launcher.partition=main launcher.gres=shard:1 \
  launcher.remote_cwd=workspace/OnePlanner \
  launcher.python=.venv/bin/python \
  "launcher.setup=['source ~/workspace/opt/env.sh']"
    • launcher.remote_cwd is where every job -- each task and the collect job -- works on the node. A relative path is relative to the job user's home on the node, ~/... is that home too, and an absolute path is used as it is. It is expanded by the job script on the node, never here: the home is the one the node's passwd database gives the job's user (whatever $HOME the job was handed), so the user name and home may differ from the submit host's.
    • launcher.python is then required: the submit host's interpreter is not the node's. A relative path (.venv/bin/python) is relative to remote_cwd, a bare name (python3) is looked up on the node's PATH as setup leaves it.
    • The batch's output directory must lie under the directory scenario runs in (outputs/<date>/<time>/ does), which is what the node sees at remote_cwd; scenario refuses a batch elsewhere. The manifest records it relative to that directory (batch_dir_relative, a version 2 manifest), and the jobs find it under their own working directory. On the submit host, scenario-slurm takes the batch's directory as this host sees it (scenario-slurm wait ~/mnt/node/OnePlanner/outputs/<date>/<time>), and resubmit submits with the settings the batch was submitted with.
    • Nothing of the submit host's environment reaches the job: export is NONE (the job starts with the environment SLURM gives it on the node, which on most clusters is the user's login environment) and env_passthrough is empty, unless either is set. Set the node's environment with setup, which runs in remote_cwd and may read unset variables (source ~/workspace/opt/env.sh, module load cuda, source .venv/bin/activate), and env.
    • SLURM writes a job's output before the job knows where the batch is: each job starts in /tmp with its output there (/tmp/acs-slurm-<user>-<job>_<task>.out on the node) and sends it on to the batch's slurm/logs/ once it is in remote_cwd. The file in /tmp keeps what came before (a remote_cwd the node does not have) and what SLURM itself writes (a time limit, a cancel).
    • A case's config that resolves to absolute paths -- an ODD file in a scenario package, a map -- resolves to the node's paths there; see below for when that is still the same config.

    Without remote_cwd the batch is submitted and run exactly as before (a version 1 manifest).

    A value that is a path may differ and still be the same config. That is the case when it is the submitting directory's path seen from the job's working directory (<cwd>/x there, <remote_cwd>/x here), or when it names a file with the content it had where the batch was submitted: scenario records the SHA-256 of every file an absolute path in a case's config names (the manifest's files), and the task compares the file its own config names. A file missing on the node, or with other content, is refused, naming the key and both paths. This holds with or without remote_cwd: a package installed in another environment names its files at other paths too.

    Ports¶

    Each task's CARLA needs ports no other CARLA on the node uses, and a user may run one on the defaults (2000, TrafficManager 8100). A task takes a slot of 10 ports from port_base:

    Port
    base+0 CARLA RPC (server.port)
    base+1 CARLA streaming (-carla-streaming-port)
    base+2 CARLA secondary (-carla-secondary-port)
    base+3 TrafficManager (traffic_manager.port)
    base+4 the Autoware bridge the run hosts (autoware.address)
    base+5 the driver bridge the run hosts (driver.bridge.address)

    The slot a task tries first is its array job id plus its task id, so the tasks of an array start on different slots. It takes one only when no other task holds it (an exclusive lock, <lock dir>/autoware_carla_scenario-port-<base>.lock, which goes when the task's process does) and none of its ports is bound; else the next. The lock directory must be one every job on the node sees, which /tmp is not where SLURM gives each job a private one (job_container/tmpfs): it is /dev/shm/acs-slurm-ports-<uid> (or /tmp where that cannot be made), or launcher.port_lock_dir. The default range, 20000-29999, is below Linux's ephemeral ports.

    driver.address is not changed: a policy the run serves itself (driver.policy) listens on a port the OS picks, and one it does not is a server someone else runs, which every task dials. driver.transport is not changed either: with direct a task calls the policy it serves without a socket, and with unix it serves it on a socket in a directory of its own (under $TMPDIR, which SLURM does not set by default, so usually /tmp), so neither needs a port of the slot and tasks sharing a node never meet; a unix: driver.address someone else serves is dialled by every task, as a TCP one is.

    Limits¶

    • Memory. A task runs a CARLA (about 6 GB resident) and a scenario process (about 6 GB with a TensorRT driver policy loaded). Without cgroups, SLURM uses --mem only to schedule, so set it, and array_parallelism, to what the node has.
    • Shared state. The tasks share the map caches (~/autoware_data/maps), the map files a driver policy reads (driver.map_dir) and the batch's output directory, so these must be on a file system every node sees. Map files, and the OpenDRIVE a run captures from the loaded world on a map's first run, are written atomically, so tasks that fill a cache at once do not break it. A driver policy's own caches are its own: one that two processes cannot load at once (OnePlanner's TensorRT engines, whose identity file is written under one temporary name, so two loads at the same moment fail one case with filesystem error: cannot rename) needs start_stagger_seconds, enough for one task to load it before the next starts (30 s for OnePlanner, which loads it once a task).
    • ROS 2 and Autoware egos (ego.entity=ros2, ego.entity=autoware with a launcher) run their stacks on DDS, whose domain the tasks would share; give each its own ROS_DOMAIN_ID (the Autoware launcher's ros_domain_ids), or run such batches locally.
    • File names. A case is named by its position in the batch, which is the name a local batch gives it whenever every earlier case opened its trajectory log. A case that raises before it opens it (while its ego is created or the world is set to synchronous mode) leaves its name to the next case in a local batch; under SLURM every case keeps its own.
    • build_scenario_fn. A batch run from code with a build_scenario_fn is run by the tasks only when that function can be imported by name.
