    Usage Guide¶

    This guide explains how to use the autoware-carla-scenario package to run autonomous driving scenario tests in CARLA simulator.

    CLI Commands Overview¶

    The package provides these CLI commands:

    Command Framework Purpose
    scenario Hydra Run autonomous driving scenario tests in CARLA
    scenario-new argparse Scaffold a standalone scenario package
    scenario-check Hydra compose Compile scenarios with Codon without running them (the static check the runner makes before a run)
    scenario-slurm argparse Follow, collect, resubmit or cancel a batch run as SLURM array jobs (launcher=slurm)
    scenario-odd argparse Check an ODD and show its buckets; scenario-odd route checks scenarios' planned routes against it on the Lanelet2 map
    detect-no-3d-model argparse Detect lanelets without a matching 3D ground model in CARLA
    viewer FastAPI + Uvicorn Web UI for browsing and monitoring scenario test results
    scenario-editor FastAPI + Uvicorn Web UI for authoring scenarios and exporting reproducible packages

    viewer and scenario-editor are separate applications on separate ports, and neither starts the other.

    scenario - Scenario Runner¶

    Runs autonomous driving scenario tests in CARLA. Uses Hydra for configuration management. Requires a running CARLA server.

    How It Works¶

    1. Parses the scenario=... argument (supports glob patterns for batch execution)
    2. Composes a Hydra config from map, server, ego, entity, and scenario configs
    3. Compiles the scenario with Codon and refuses it if it does not type-check (Static Check; typecheck=off skips it)
    4. Connects to the CARLA server and loads the specified map (OpenDRIVE or built-in)
    5. Spawns the ego vehicle at the configured Lanelet2 position (converted to CARLA coordinates)
    6. Enables synchronous mode (fixed 20 Hz tick rate) and starts the native CARLA recorder
    7. Runs a warm-up phase (5 ticks for physics stabilization)
    8. Enables autopilot and applies initial speeds
    9. Executes the main tick loop, checking pass/fail conditions each tick
    10. Writes the results as JSON, and the run's trajectory log as it goes
    11. Reloads the CARLA world for clean state between scenarios

    Basic Usage¶

    # Run a single scenario
uv run scenario scenario=intersection_passing/straight

# Run a left-turn variant
uv run scenario scenario=intersection_passing/left_turn

# Run traffic light compliance scenario
uv run scenario scenario=traffic_light_compliance/traffic_light_compliance

# Run a lane change scenario
uv run scenario scenario=lane_change/left

# Run a temporary stop scenario
uv run scenario scenario=temporary_stop/temporary_stop

    Batch Execution with Glob Patterns¶

    When the scenario= value contains glob metacharacters (*, ?, [), all matching scenario configs are executed sequentially in a single CARLA session:

    # Run all intersection-passing variants
uv run scenario scenario='intersection_passing/*'

# Run all scenarios matching a partial pattern
uv run scenario scenario='intersection_passing/left_*'

# Run all lane-change scenarios
uv run scenario scenario='lane_change/*'

# Run everything
uv run scenario scenario='*/*'

# Run every lane-change scenario, however deep below lane_change/
uv run scenario scenario='lane_change/**'

    The pattern is matched as scenario/{pattern}.yaml under each config directory: * stays within one path component, and a ** component crosses them. A trailing ** means everything below it and is read as **/*, so lane_change/** and ** select every config below lane_change/ and scenario/. A ** inside a component (lane_change/**left) is refused with an error naming the pattern, and so is a pattern that could reach outside scenario/: one starting with / (/lane_change/*) or with a .. component (../*). The pattern means the same on every supported Python version, and the viewer's Run form reads it the same way.

    Batch constraints:

    • All scenarios in a batch must share the same map (CARLA loads one map per session)
    • Results are written to outputs/YYYY-MM-DD/HH-MM-SS/batch_results.json
    • A summary table is printed at the end with per-scenario pass/fail status
    • A case that cannot run at all -- its run raises on every attempt (server.cooldown_max_retries), e.g. a spawn point with no ground under it -- does not end the batch: it is reported as [ERROR] with the error, its batch_results.json entry is "passed": false with "error": true, and the batch goes on with the next case. Ctrl+C still stops the batch
    • A scenario with a sweep: section runs once, as configured; add --multirun to run every case of it (see Running every sweep case in a batch)

    Running every sweep case in a batch¶

    With --multirun, a batch expands each scenario's sweep: -- lanelet constraints, a route search, the ODD sampler -- into its cases, the same ones scenario-expand prints, and runs them all in the one queue, against one CARLA session (and, with autoware.launcher, a fresh Autoware per case):

    # Every lanelet case of both cut-in scenarios
uv run scenario --multirun 'scenario=cut_in/*' map=town10hd_opt

# 10 cases per scenario drawn from the ODD
uv run scenario --multirun 'scenario=cut_in/*' map=town10hd_opt \
  +sweep.odd_sample.count=10 +sweep.odd_sample.strategy=coverage

    Scenarios that draw from one ODD go on from each other's draws rather than each draw the same cases: with strategy: coverage a later scenario aims at what the earlier ones left uncovered (see Sampling scenarios from the ODD).

    A scenario with more than one case is listed as name#k in the summary, and batch_results.json gives each case its overrides. hydra/sweeper=... may be given but is not needed: the batch is the sweeper.

    On a SLURM cluster, launcher=slurm runs a batch's cases as array jobs, several at once, each on a CARLA of its own, with the same outputs (off unless selected; see Running a Batch on SLURM):

    uv run scenario --multirun 'scenario=cut_in/*' +sweep.odd_sample.count=24 \
  launcher=slurm launcher.array_parallelism=2

    Resetting the world between cases¶

    Between two cases of a batch (and between two cases of a SLURM task) the world is reset, so that nothing of one case is in the next. server.world_reset says how:

    server.world_reset What happens Cost per case (CARLA UE5, Town10HD_Opt)
    reload (default) The map is loaded again: a new episode ~5 s
    soft The map stays loaded; the world is put back as it was right after the load well under a second 
    uv run scenario --multirun 'scenario=cut_in/*' map=town10hd_opt server.world_reset=soft
# Soft resets, with a full reload on every 10th reset anyway
uv run scenario --multirun 'scenario=cut_in/*' map=town10hd_opt \
  server.world_reset=soft server.reload_every=10

    soft is opt-in: it is not yet shown that every case gives the same result after a soft reset as after a reload (#282). Compare a sweep run both ways before relying on it, and keep reload for results that have to be order-independent until that is shown for your scenarios.

    What a soft reset does. Right after the map is loaded (at the start, and after every reload) the runner reads a baseline off the world: its actors, the episode settings, the weather, every traffic light's green, yellow and red times and whether it is frozen, and the spectator's transform. A soft reset then, in this order:

    1. stops the CARLA recorder (the run stops its own already; this catches one a failed run left going);
    2. destroys every actor the baseline does not list -- sensors and controllers first, then walkers, vehicles and anything else (props, an ego an external stack spawned) -- and ticks the world. Traffic lights, traffic signs and the spectator are the map's and are never destroyed;
    3. gives every traffic light its baseline timing back, resets all of them to the start of their cycle (World.reset_all_traffic_lights()) and freezes or unfreezes each as it was;
    4. puts the weather and the spectator back, and ticks the world;
    5. checks that no actor outside the baseline is left and that none of the map's is gone;
    6. applies the baseline episode settings (asynchronous, as a loaded world is; the next run makes it synchronous again).

    What the run itself cleans up is cleaned up as before, whatever the reset: the ego, the conditions' sensors, the props, the T4 and Rerun sensors, the recorder, and the traffic backend (closed after every run, which is what resets the TrafficManager).

    When it loads the map instead. The map is loaded, as with reload, when

    • there is no baseline (the map was not loaded by this runner yet, or reading the baseline failed);
    • the server runs another episode than the one the baseline was read in: another client loaded a world -- another map, or the same one -- on the server;
    • any step above raises, an actor survives its destroy, or an actor of the map is gone;
    • the world has a traffic light the baseline does not list (the server listed it only after the baseline was read): its timing and frozen state are not known, so whatever a case did to it could not be put back;
    • server.reload_every is N > 0 and N - 1 soft resets have been done since the last load (every N-th reset is a reload; 1 is the same as reload).

    A reload reads a new baseline, so the resets after it are soft again.

    What a soft reset cannot guarantee. These differ from a reload, and a scenario whose result depends on them can give a different result after a soft reset:

    • The episode goes on. The frame number and the episode's elapsed time keep counting, and actor ids keep growing (a fresh episode starts both again). The runner measures a case on its own clock from its first tick, so its conditions and timeouts do not see this, but anything that reads raw frame numbers, elapsed_seconds or actor ids does.
    • Traffic light phase. The lights are reset to the start of their cycle, which is where a load leaves them too, but how far into it they are on the case's first tick may differ by the ticks the reset itself takes.
    • Vehicle and physics state. The previous case's vehicles are destroyed and new ones spawned, but state the server keeps outside an actor (physics scene, pooled resources) is not reset. In the trials behind #282 an ego's gear differed on every tick from a fresh-world run of the same case.
    • What has no getter in the CARLA API. Map layers unloaded with World.unload_map_layer(), environment objects toggled with enable_environment_objects(), street lights switched through the LightManager, the pedestrians' cross factor and seed, and debug drawings still within their life_time. The framework changes none of these but the pedestrians' cross factor, which it puts back itself after starting each walker; a scenario that changes the others needs reload.
    • The TrafficManager. It lives outside the episode, so a reload does not reset it either: the traffic backend's close() after each run is what does.

    server.world_reset applies to the cases one batch runs in one queue (--multirun with a glob or a sweep:, and the cases of one SLURM task). A Hydra sweeper such as hydra/sweeper=lanelet_constraint runs each case as a job of its own, which loads the map when it starts, so there is nothing to reset between its cases.

    Selecting a Published HD Map¶

    A map group can name a git repository instead of local files, and the map is fetched into ~/autoware_data/maps on first use -- the same directory Autoware's own setup downloads maps into, so a machine that has run it clones nothing:

    # Town10HD_Opt, as published for CARLA 0.10, pinned to a commit. The built-in
# scenario configs name Nishishinjuku lanelets, so place the ego on Town10's.
uv run scenario scenario=lane_change/left map=town10hd_opt \
  ego.spawn_lanelet_id=324 ego.spawn_s=10.0 ego.goal_lanelet_id=5650

# Any repository, any revision
uv run scenario map=town10hd_opt \
  map.source='git+https://huggingface.co/datasets/OWNER/NAME@REF#maps/T'

# A map directory on this machine, read in place
uv run scenario map=town10hd_opt map.directory=/path/to/autoware_maps/Town10HD_Opt

    See HD Maps from a Git Repository.

    Lanelet Constraint Sweeping¶

    The package ships a Hydra Sweeper plugin (hydra/sweeper=lanelet_constraint) that expands a single scenario config into one job per lanelet that matches a set of constraints, optionally deriving per-job parameters via "bindings". Each scenario YAML may declare its own sweep: section (see traffic_light_compliance.yaml for an example).

    sweep.constraints sweeps one parameter: it holds a single target key (such as ego.spawn_lanelet_id) with its list of constraints, and every other parameter a case needs is derived from the matched lanelet by sweep.bindings. A sweep.constraints with a second key is refused with an error when the sweep is expanded, rather than searched together with the first.

    # Run a Hydra multirun over every lanelet whose `ego.spawn_lanelet_id`
# satisfies the scenario's `sweep.constraints`.
uv run scenario --multirun scenario=traffic_light_compliance/traffic_light_compliance \
  hydra/sweeper=lanelet_constraint

# Resume a sweep from job number N (1-indexed; 0 disables).
uv run scenario --multirun scenario=traffic_light_compliance/traffic_light_compliance \
  hydra/sweeper=lanelet_constraint sweep.resume_from=10

    Sweeps write results under multirun/YYYY-MM-DD/HH-MM-SS/<job-index>/, not outputs/. The result viewer scans both directories.

    A failed, crashed or timed-out case does not stop the sweep: every case runs, the sweeper logs Sweep complete: P/N succeeded, F failed (T timed out)., and the process then exits 1 when any case failed (see Exit Codes).

    The sweeper runs each case in a forked process of its own. With server.cooldown_max_retries it runs a case again only when it could not run: its run raised (CARLA went away, a spawn failed), timed out (sweep.job_timeout_seconds) or crashed. A case whose scenario ran to a FAILED verdict is final and is not retried, as in a batch. The sweeper owns these retries: the case's own queue does not retry it as well, so a case runs at most 1 + server.cooldown_max_retries times, as in a batch.

    A case that timed out or crashed had no chance to stop the CARLA server it launched; that server's watchdog stops it within about a second, giving it 10 s before SIGKILL. So before the next attempt -- a retry or the next case -- the sweeper waits until the CARLA processes the case launched have exited (at most 15 s, then it kills them), on top of server.cooldown_seconds: the next case must neither reuse the dying server nor start one while it still holds the port, even if the case was killed while its server was still loading. A case that ended normally stopped its server itself, so nothing is waited for; nor is a server the case did not launch (one you started yourself, which it reused), which no case stops.

    A sweep with no case to run exits 1 before anything runs, as a batch with no case left does: its constraints, route or ODD sample match nothing on the map (the sweep expands to no case), or --resume-from / sweep.resume_from is past its last case.

    Ctrl-C or SIGTERM stops the sweep and the case it is running. The case is sent SIGTERM, so it stops its CARLA server and Autoware stack as on Ctrl-C, and SIGKILL if it is still running 30 s later (a second Ctrl-C does not wait). The sweep then exits 130 (Ctrl-C) or 143 (SIGTERM) and names the case to resume from.

    To get the concrete scenarios without running them (for example, to fan them out over a cluster), use scenario-expand. It takes the same arguments as scenario and prints JSON with one list of Hydra overrides per concrete scenario. These are the same cases, in the same order, that the sweeper runs:

    uv run scenario-expand scenario=traffic_light_compliance/traffic_light_compliance
# {"scenario": "...", "cases": [["ego.spawn_lanelet_id=5", "ego.spawn_s=18.62..."], ...]}

    A scenario without a sweep: section is already concrete, so it expands to a single empty case. Only the Lanelet2 map is needed, not a CARLA server.

    A logical scenario -- a document with a route search, whose sweep: holds route: instead of constraints: -- expands to one case per route of the map that matches its pattern, each with the ego's spawn and goal and the match itself (scenario.route.*); see Logical Scenarios from Routes.

    Resume from a Specific Scenario¶

    When running large batches, you can skip already-completed scenarios. --resume-from N starts at the Nth scenario (1-indexed, as for a sweep); in a --multirun batch it counts the expanded cases:

    # Resume from the 3rd scenario
uv run scenario scenario='intersection_passing/*' --resume-from 3

    Overriding Configuration Parameters¶

    Any nested Hydra parameter can be overridden from the command line:

    # Select a different map
uv run scenario scenario=intersection_passing/straight map=nishishinjuku

# Connect to a remote CARLA server
uv run scenario scenario=intersection_passing/straight server.host=192.168.1.100 server.port=3000

# Change ego vehicle type and speed
uv run scenario scenario=intersection_passing/straight \
  ego.vehicle_type=vehicle.tesla.model3 \
  ego.initial_speed_kmh=30.0

# Override scenario-specific parameters
uv run scenario scenario=intersection_passing/straight scenario.timeout_seconds=15.0

# Change Traffic Manager port
uv run scenario scenario=intersection_passing/straight traffic_manager.port=8200

    One Seed for the Whole Run¶

    seed (top level, 0 by default) is the one number every random draw of a run follows, so the same seed runs the same scenario again:

    uv run scenario scenario=intersection_passing/straight seed=42

    It is the seed of:

    What draws Its own seed, which wins when set
    The cases a sweep draws from the ODD (sweep.odd_sample), and the grip and visibility drawn for each sweep.odd_sample.seed
    The scenario: BaseScenario.random_seed --
    The traffic backend: CARLA's TrafficManager (set_random_device_seed, each vehicle's parameter draws), SUMO (--seed, netconvert --seed, its own draws) -- (the scenario's)
    CARLA's pedestrian navigation (World.set_pedestrians_seed) -- (the scenario's)
    Background traffic background_traffic.seed
    The adversarial actions, AdversarialTrafficAction, AdversityFeasibleCondition, TrafficSourceAction their seed argument (Seed in the editor)
    The driver policy's session (DriveSessionRequest.random_seed) driver.random_seed
    A LiDAR's weather noise driver.lidars[].noise_seed

    Every one of those seeds is null (None in Python) by default, and a null seed is the run's. In Python the run's seed lives in autoware_carla_scenario.seed: the runner sets it from the scenario's random_seed before setup() (and scenario sets it from the config before it builds the scenario), and a component built with seed=None takes it when it is built. A scenario that draws for itself seeds its own generator from self.random_seed.

    A route search's seed (sweep.route.seed) is not one of them: unset, the matches are not shuffled at all. A config with no seed key (a scenario package's own config.yaml written before it existed) leaves the scenario the random_seed it was built with.

    Root Configuration (config.yaml)¶

    Defines the default config group composition:

    Default Group Default Value Description
    server localhost CARLA server connection
    ego default Ego vehicle configuration
    entity default Entity spawn and ground projection
    traffic_manager default CARLA Traffic Manager
    scenario intersection_passing/left_turn Scenario to run
    map nishishinjuku Map to load

    Server Configuration¶

    Parameter Type Default Description
    server.host str localhost CARLA server hostname
    server.port int 2000 CARLA server port
    server.cooldown_seconds float 2.0 Wait time between consecutive scenario runs
    server.cooldown_max_retries int 0 Maximum retries of a run that raised (not of one that ran and failed)
    server.world_reset str reload How the world is reset between a batch's cases: reload or soft (see Resetting the world between cases)
    server.reload_every int 0 With world_reset: soft, load the map on every N-th reset anyway; 0: only when a soft reset cannot be done

    Ego Vehicle Configuration¶

    Parameter Type Default Description
    ego.vehicle_type str vehicle.mini.cooper CARLA blueprint ID for ego vehicle
    ego.initial_speed_kmh float 0.0 Initial speed of ego vehicle (km/h)
    ego.spawn_lanelet_id int 242 Lanelet ID for spawn position
    ego.spawn_s float 25.0 Longitudinal offset along lanelet centerline (meters)
    ego.spawn_t float 0.0 Lateral offset from the lanelet centerline, positive to its left (meters)
    ego.spawn_heading float 0.0 Yaw relative to the lanelet's direction of travel, positive anticlockwise (radians)

    Entity Configuration¶

    Controls ground projection (ray casting) and spawn retry behavior:

    Parameter Type Default Description
    entity.ground_projection_ray_distance_upper float 5.0 Ray search range above estimated z (meters)
    entity.ground_projection_ray_distance_lower float 10.0 Ray search range below estimated z (meters)
    entity.spawn_retry_max_count int 10 Maximum retry attempts for spawn
    entity.spawn_retry_t_step float 0.1 Lateral offset shift per retry (meters)
    entity.spawn_retry_z_step float 0.5 Vertical shift per retry (meters)

    Traffic Manager Configuration¶

    Parameter Type Default Description
    traffic_manager.port int 8100 CARLA Traffic Manager RPC port

    Seeing a run¶

    A run renders no video (since 15.0.0). What it leaves to look at is its trajectory log, {ScenarioName}.trajectory.jsonl: every vehicle and pedestrian tick by tick, the traffic lights, the map it ran on, the ego's plan (its debug markers), each condition's state and the verdict (Trajectory Log). To see it, make it a Rerun recording, {ScenarioName}.rrd beside the log, and open that in the Rerun viewer. The conversion is the autoware-carla-scenario-rerun package, installed with the rerun extra:

    # The converter (rerun), and the Rerun viewer its recordings are made for (viewer):
pip install 'autoware-carla-scenario[rerun,viewer]'
# A recording of every run, made as each run ends:
uv run scenario scenario=cut_in/cut_in rerun.enabled=true
uv run scenario 'scenario=cut_in/*' --multirun rerun.enabled=true
rerun outputs/2026-10-18/08-48-12/CutInScenario-3.rrd     # the Rerun viewer
    Parameter Type Default Description
    rerun.enabled bool false Convert each run's trajectory log into {ScenarioName}.rrd as soon as the run ends
    rerun.strict bool false Fail the conversion of a log with a record type or a field the converter does not know, rather than skip it with a warning
    rerun.lidar bool false Put the LiDAR sweeps the ego's driver policy gets into the recording too (Sensors)
    rerun.lidar_max_points int 65536 At most this many points of a sweep (an even subsample); 0 keeps them all
    rerun.cameras bool false Put the camera frames the ego's driver policy gets into the recording too (Sensors)

    With rerun.enabled=true:

    • A run asking for recordings without the extra installed is refused before anything starts (exit code 2), saying how to install it.
    • Each log is converted on a background thread as soon as its run ends, while the next case runs (the converter releases the GIL; a log takes milliseconds). A run that raised is converted too: its log is what shows what happened.
    • At the end the run waits for the last conversions and prints how they went: Rerun recordings: N/M written, and a line per failure naming its case. A failed conversion does not change any verdict or the exit code.
    • Each case's {ScenarioName}_result.json names its recording (rerun_recording), and so does its entry in a batch's batch_results.json, with rerun_error when the conversion failed. The viewer's scenario page shows it in the embedded Rerun viewer, without converting the log again (Seeing a run in the viewer).
    • A Hydra sweep (--multirun without a glob) runs each case in a process of its own, and each converts its own log. So does each task of a batch run on SLURM (launcher=slurm, Running a Batch on SLURM): it converts its own cases, and scenario-slurm collect reports their recordings as a local batch does.

    A T4 dataset of a run¶

    With t4.enabled=true each run is also written as a T4 dataset, {ScenarioName}.t4/, which t4-devkit reads: the sweeps and frames of the driver policy's sensors (driver.lidars, driver.cameras) at each policy step, and the box of every vehicle and pedestrian from CARLA's ground truth (the t4 extra; T4 Dataset).

    A T4Scene of a run¶

    With t4scene.enabled=true each run's trajectory log is also written as a T4Scene, {ScenarioName}.t4scene.pb with its map, {ScenarioName}.t4scene.map.pb, the scene tier4/e2e-devkit decodes, scores and draws (T4 Scene); scenario-t4scene <output dir> does the same after a run.

    Sensors in the recording¶

    The trajectory log holds no sensor data. With rerun.enabled=true and:

    • rerun.lidar=true, the sweeps each driver LiDAR sends the ego's policy (driver.lidars) are recorded as world/lidar/<logical id>: points in the recording's world frame, coloured by height above the ego, drawn where the ego's pose put them when the policy got them;
    • rerun.cameras=true, the frames each driver camera sends it (driver.cameras) are recorded as world/ego/pose/cameras/<logical id>: the camera's mount on the ego and a pinhole of its field of view, so the 3D view draws its frustum with the frame in it, and the JPEG frames the policy got (a 2D view of the entity shows them).

    They are written during the run into {ScenarioName}.sensors.rrd; once the log is converted they are merged into {ScenarioName}.rrd (rerun rrd merge) and that file is removed. It needs the Rerun SDK of the converter's version:

    pip install 'autoware-carla-scenario[rerun-lidar]'
uv run scenario scenario=cut_in/cut_in driver=... rerun.enabled=true \
    rerun.lidar=true rerun.cameras=true

    Points are most of a recording: about 0.8 MB a sweep at the default 65,536; a camera frame is its JPEG (driver.image_quality). A merge that fails keeps {ScenarioName}.sensors.rrd beside the recording (logged; not a failed conversion); converting the run again (below) merges it. The two cannot be opened together instead: the viewer registers a file by its recording id, and the second replaces the first.

    A run made without it (or by a version before it) can be converted afterwards, the same way:

    # Every run of a session (a sweep's directory works the same), or one log:
python -m autoware_carla_scenario.rerun outputs/2026-10-18/08-48-12
python -m autoware_carla_scenario.rerun outputs/2026-10-18/08-48-12/CutInScenario-3.trajectory.jsonl

    or from Python, autoware_carla_scenario.rerun.convert_outputs(path). It also converts a run again (with --strict, or a newer converter), and keeps the sensors the run recorded:

    • a {ScenarioName}.sensors.rrd left beside the log (a merge that failed) is merged into the new recording and removed, as during a run;
    • the sensors in a {ScenarioName}.rrd it replaces (world/lidar/**, world/ego/pose/cameras/**) are carried over into the new one. That needs the Rerun SDK's CLI (rerun-lidar extra); without it, or if it fails, the old recording is left as it was and reported as [SKIPPED] (exit status 1). --overwrite (overwrite=True) replaces it anyway, without its sensors.

    A log that fails to convert leaves the recording it would have replaced as it was. The converter reads nothing but the log and the map files the log names, so it runs anywhere, without CARLA. The CARLA recording ({ScenarioName}.log) is still written: CARLA's own replayer (client.replay_file()) plays it back on a server running the same map.

    video.* settings (video.enabled, video.width, video.height) are accepted for old command lines and configs, and do nothing: a run that sets one warns that it is ignored and says the above.

    Traffic Light Compliance¶

    Tests that the ego vehicle correctly stops at a red light and proceeds after green.

    Config

    Scenario-specific parameters:

    Parameter Type Default Description

    scenario.timeout_seconds float 8.0 Maximum scenario duration
    scenario.stop_zone_min_m float 0.0 Near end of the stop zone: metres before the stop line (stop_line_distance_m)
    scenario.stop_zone_max_m float 3.0 Far end of the stop zone; standing still farther back until the green fails the run
    scenario.stop_line_tolerance_m float 0.0 How far the front bumper may pass the stop line on red before the run fails for running the red; that far past counts as at the line for the stop zone

    Scenario Evaluation¶

    Each scenario registers pass conditions and fail conditions. The tick loop evaluates them every frame:

    • First pass condition satisfied → scenario passes
    • First fail condition triggered → scenario fails
    • Common fail conditions: TimeoutCondition (exceeded time limit), EntityExistenceCondition (ego destroyed)

    ODD and Coverage¶

    Every run is measured against an ODD, named by the odd key (default unless overridden). Its attributes are sampled on every tick and written, with the scenario's own cover items, to {ScenarioName}_coverage.json. scenario-coverage outputs/ merges those files into a report. See ODD and Coverage.

    uv run scenario scenario=intersection_passing/left_turn odd=path/to/urban.yaml
uv run scenario-coverage outputs/ --markdown coverage.md

    Before running, scenario-odd route plans each scenario's ego route on the Lanelet2 map (no CARLA server) and reports which parts of it are outside the ODD, which are undecided until run time, the metres it is expected to cover in each bucket, and the buckets no route reaches (Checking a planned route):

    uv run scenario-odd route path/to/urban.yaml 'intersection_passing/*' lane_change/left

    Output Files¶

    Each scenario run generates output in outputs/YYYY-MM-DD/HH-MM-SS/:

    File Description
    {ScenarioName}.log CARLA native recording (replay format)
    {ScenarioName}_result.json Machine-readable result with condition statuses
    {ScenarioName}_coverage.json ODD and scenario coverage hits of the run (merge with scenario-coverage, see Coverage)
    {ScenarioName}_odd.tar.gz The run's ODD as the files it was read from (an ODD read from OpenODD YAML; openodd's transmission archive, named by its revision; see Versions of an ODD)
    {ScenarioName}_requirements.lock What the run ran with: every installed distribution pinned, in the requirements format (pip install -r), headed by the framework, the scenario's package, Python and the platform. A distribution from git is pinned to its commit; an editable one (a checkout) names its directory, commit and whether it had uncommitted changes
    {ScenarioName}_environment.json The same, structured; _result.json carries its summary (environment: the framework, the scenario's package, key dependencies, and the lock's id -- the SHA-256 of what it pins -- so runs on one environment can be found by it)
    {ScenarioName}.trajectory.jsonl The run, tick by tick, and the map, plan, conditions and verdict (Trajectory Log); make it a Rerun recording to see the run (Seeing a run), or a T4Scene for tier4/e2e-devkit with scenario-t4scene (T4 Scene)
    {ScenarioName}.rrd The Rerun recording of the trajectory log, with rerun.enabled=true (Seeing a run)
    {ScenarioName}.t4scene.pb, {ScenarioName}.t4scene.map.pb The trajectory log as a T4Scene and the map it names, with t4scene.enabled=true (T4 Scene)
    batch_results.json Batch summary (glob/batch mode only)

    Result JSON format:

    On a pass, message is the message of the pass condition that fired -- here an AndCondition of two StickyConditions, which joins its children's messages with AND -- or Scenario completed successfully when is_done() ended the run. When a fail condition ends the run, it is that condition's message.

    {
  "scenario": "intersection_passing/straight",
  "passed": true,
  "message": "Entity 'ego' is on road '5' (any lane) (s=12.40, t=-1.75) at 1.10s AND Entity 'ego' is on road '12' (any lane) (s=3.05, t=-1.80) at 3.42s",
  "elapsed_seconds": 3.42,
  "condition_statuses": [
    {"label": "Road 5 visited", "satisfied": true, "message": "..."},
    {"label": "Road 12 visited", "satisfied": true, "message": "..."}
  ]
}

    Why a run failed:

    A failed run's result has a failure: the fail condition that ended it, and a category that names what went wrong the same way in every scenario, where the condition's label is the scenario author's. A batch, a sweep or two versions of a driver can then be compared by what went wrong (batch_results.json carries it for every case, and the summary prints it).

    "failure": {
  "condition": "fail[1](scenario_timeout)",
  "category": "progress",
  "at": 25.0,
  "message": "Timeout after 25.00s (limit: 25.0s)",
  "detail": "stalled",
  "also_triggered": []
}
    Category What went wrong
    collision The ego hit something
    traffic_rule It broke a traffic rule: ran a red light, drove against the traffic
    signalling It did not signal what it did (no turn indicator)
    lane_keeping It left its lane or the road
    stability It did not drive steadily: sawed at the steering, weaved, flicked its indicators
    safety_margin It came too close: time to collision, headway, distance
    progress It did not get where the scenario asked in time
    driver The driver ended the run itself
    infrastructure The run could not go on: the ego vanished, or the run raised
    other None of these, or a condition that does not say

    A scenario gives a fail condition its category when it registers it:

    from autoware_carla_scenario.failure import FailureCategory

self.register_fail_condition(
    PersistentCondition(AndCondition([...]), 0.5, label="no_left_indicator"),
    category=FailureCategory.SIGNALLING,
)

    Without one, the condition says (BaseCondition.failure_category()): a collision condition is collision, a timeout progress, a time-to-collision or headway condition safety_margin, the ego's existence infrastructure, and a MetricCondition what its metric reads (the collision metrics collision, offroad lane_keeping, wrong_lane traffic_rule, the weaving ones stability). A sticky or persistent condition says what it wraps. A combination of conditions (AND, OR, NOT) says nothing, and the run's failure is other: give it a category.

    detail tells a progress failure apart by how the ego ended the run: never_moved (it never drove 1 m), stalled (it had stood still for 3 s or more: waiting for something that never cleared) or moving (it was driving, but not where the scenario's pass condition asked). The other fail conditions that held when the run ended are in also_triggered. The driver ending the run is driver, and a case that raised on every attempt is infrastructure.

    Exit Codes¶

    Code Meaning
    0 All scenarios passed
    1 One or more scenarios failed or errored, or configuration/runtime error
    2 Refused before anything ran: the scenario does not type-check, or an extra it asks for (rerun, t4) is not installed
    130, 143 Stopped by Ctrl-C (130) or SIGTERM (143), after the run stopped what it started (its CARLA server, its Autoware stack); a sweep first stops the case it is running

    The same codes hold however the cases run: a single run, a glob batch, a --multirun (each case of the scenario's sweep in one batch, hydra/sweeper=lanelet_constraint, or Hydra's own sweeper over comma-separated values) and launcher=slurm, which waits for the array and collects it. A sweep runs every case before it exits, so 1 means at least one case failed; the summary names how many. A refusal ends a sweep at once with 2, since every case after it would be refused too. A run with no case to run (nothing expanded, or --resume-from past the last case) exits 1: exit 0 always means something ran and passed. The exceptions:

    • Under Hydra's own sweeper (scenario --multirun key=a,b, no hydra/sweeper=), a case that raises an exception ends the sweep at once with 1, as Hydra does; a case that runs and fails does not.
    • launcher=slurm with --no-wait exits 0 once the batch is submitted; its verdict is what scenario-slurm wait or scenario-slurm collect exit with. Interrupted while it waits, it cancels the array and exits with the verdict of what it collects (slurm.cancel_on_interrupt, the default), or exits 130 and leaves the array running.

    Driving the Ego with an External Policy¶

    By default CARLA's TrafficManager drives the ego. To hand it to an external driving policy over the egodriver gRPC contract instead, start the policy server and select the carla_driver entity:

    # 1. Start the policy (in its own environment)
uv run carla-driver-interface serve --policy route_follower --port 50051

# 2. Run any scenario against it
uv run scenario ego.entity=carla_driver driver.address=localhost:50051

    ego.entity accepts:

    Value Behaviour
    autopilot (default) CARLA's TrafficManager drives the ego
    autoware Autoware drives the ego, over the AutowareBridge; with autoware.launcher the framework starts a fresh Autoware per scenario (Autoware as the Ego)
    carla_driver An external policy drives the ego
    ros2 ROS 2 nodes drive the ego over DDS, with no bridge node (ROS 2 over DDS)
    hils ECUs under test drive the ego, through the resident HILS bridge scenario-hils (hils.host, hils.port; HILS Bridge)

    Common overrides:

    # Query the policy every simulation tick instead of every other one
uv run scenario ego.entity=carla_driver driver.policy_timestep_s=0.05

# Pin the rig origin offset when the derived value looks wrong (CARLA 0.9.x)
uv run scenario ego.entity=carla_driver driver.rear_axle_offset_m=-1.4

# Send a smaller, cheaper camera frame
uv run scenario ego.entity=carla_driver \
    driver.cameras.0.image_width=480 driver.cameras.0.image_height=302

    See External Driver Interface for the full reference.

    Rendering sensors with carla_canvas¶

    carla_canvas renders cameras and LiDARs behind the CARLA API instead of the CARLA server: a configuration file names a renderer service (3D Gaussian splatting, a LiDAR world model such as LidarVerse, ...) and the sensor types it renders, and typesafe_carla's sensor plugin hands those sensors' measurements over from the service. canvas.config points a run at such a file; nothing else about the run changes -- the scenario, the driver and the measurements they read are the same:

    pip install 'carla-canvas[client]>=0.2'
uv run scenario scenario=cut_in/cut_in ego.entity=carla_driver \
    canvas.config=path/to/lidarverse.yaml
    Parameter Type Default Description
    canvas.config str null A carla_canvas configuration: its sensors are rendered by its renderer; null leaves every sensor to CARLA

    The run sets CARLA_CANVAS_CONFIG and TYPESAFE_CARLA_SENSOR_PLUGIN before any sensor listens, which is when typesafe_carla loads the plugin, once for the process: the cases of a batch name one file (a batch naming two is refused). The renderer is the configuration's: started by the plugin when nothing answers at renderer.endpoint and the file gives a renderer.command, or run by hand (carla-canvas serve --config ...). carla_canvas is not an extra of this package: it needs protobuf 7, and the vendored alpasim modules are regenerated on protobuf 4. Under SLURM the file is the nodes' path.

    scenario-hils - Streaming the Ego to ECUs (HILS)¶

    A resident process on the HILS PC that follows a run's ego in CARLA, sends ECUs under test their sensors' and buses' traffic (CAN, GNSS, LiDAR packets, camera frames) through hilspy, initializes and finalizes them around each scenario, and hands their commands back to a run with ego.entity=hils; configured by one YAML file:

    uvx --from 'autoware-carla-scenario[hils]' scenario-hils --example > hils.yaml
uvx --from 'autoware-carla-scenario[hils]' scenario-hils hils.yaml

    See HILS Bridge.

    detect-no-3d-model - 3D Model Detection¶

    Detects lanelets that do not have a matching 3D ground model in CARLA. Useful for identifying areas where vehicle ground-projection ray casting will fail. Requires a running CARLA server with the target map loaded.

    How It Works¶

    1. Reads the map configuration YAML and resolves its map files the way uv run scenario does (see Input YAML Requirements)
    2. Connects to the CARLA server and loads the map -- installing the OpenDRIVE first when map.overwrite_xodr is set, by name otherwise -- and, for a map that carries no OpenDRIVE, reads it back out of the loaded world into the map cache, as a run does
    3. For each lanelet's center point, casts a vertical ray (upward and downward from estimated z) to detect ground geometry
    4. Reports lanelets where the ray does not hit any 3D surface
    5. Writes the detected IDs to the YAML configuration's no_3d_model_lanelet_ids field

    The IDs go into no_3d_model_lanelet_ids in the YAML's map: section when it has one, and at the top level otherwise (the same place the map settings are read from). An existing value is replaced whatever its style (a block list, a flow list such as [1, 2], an empty value, null); a missing key is added after the section's last entry. The file is edited as text, so comments, ${...} interpolations and line endings are kept, and it is replaced atomically (a symlinked YAML is written through to its target). The edited text is parsed again first: if anything other than that one value would change -- or the section cannot be edited as text, e.g. map: {name: X} -- the tool exits with an error, prints the detected IDs, and leaves the file as it was.

    Usage¶

    Run it from the repository root: the example map configs live under autoware_carla_scenario/src/autoware_carla_scenario/examples/conf/map/, and nishishinjuku.yaml names its files relative to the root (data/nishishinjuku.osm).

    CONF=autoware_carla_scenario/src/autoware_carla_scenario/examples/conf/map

# Basic detection using map config YAML
uv run detect-no-3d-model $CONF/nishishinjuku.yaml

# A map named only by map.source (its OpenDRIVE is read back from CARLA)
uv run detect-no-3d-model $CONF/town10hd_opt.yaml

# Connect to a remote CARLA server
uv run detect-no-3d-model $CONF/nishishinjuku.yaml --host 192.168.1.100 --port 3000

# Increase ray search range for hilly terrain
uv run detect-no-3d-model $CONF/nishishinjuku.yaml --ray-upper 10.0 --ray-lower 10.0

# Longer timeout for slow connections
uv run detect-no-3d-model $CONF/nishishinjuku.yaml --timeout 30.0

# Debug logging
uv run detect-no-3d-model $CONF/nishishinjuku.yaml -v

    Command-Line Options¶

    Option Short Required Default Description
    yaml_path - Yes - Path to map configuration YAML (map settings at the top level or under map:; see below)
    --host - No localhost CARLA server hostname
    --port - No 2000 CARLA server port
    --ray-upper - No 5.0 Ray search range above z estimate (meters)
    --ray-lower - No 5.0 Ray search range below z estimate (meters)
    --timeout - No 10.0 CARLA client timeout (seconds)
    --verbose -v No false Enable DEBUG logging

    Input YAML Requirements¶

    The map settings are resolved exactly as the scenario runner resolves the map config group: lanelet2_path and xodr_path (~ and ${oc.env:...} work; a relative path is taken from the working directory), directory, source, projector_type and overwrite_xodr (see Map Configuration). A map given by files needs at minimum:

    name: NishishinjukuMap          # CARLA map name
xodr_path: path/to/map.xodr     # Path to OpenDRIVE file
lanelet2_path: path/to/map.osm  # Path to Lanelet2 file

    A map given by source or directory needs only that key (name defaults to the map directory's name); when it ships no OpenDRIVE, the tool reads the road network back out of the loaded CARLA world and caches it, as a run does. With overwrite_xodr: true the OpenDRIVE is installed into the CARLA asset named by the <MAP_NAME>_PATH environment variable before the map is loaded; otherwise CARLA's own road network is kept.

    These keys may also sit under a map: section (as in the example nishishinjuku.yaml, a # @package _global_ config); no_3d_model_lanelet_ids is then written there too.

    A config that cannot be read, is not valid YAML, or does not name a usable map is reported as a single detect-no-3d-model: error: ... line with exit status 1, before CARLA is contacted.

    Integration with Scenario Runner¶

    The detected lanelet IDs are stored in the map config's no_3d_model_lanelet_ids field. The scenario runner's sweep feature uses this list to exclude problematic lanelets from automatic spawn point selection.

    viewer - Scenario Result Viewer¶

    Web UI for browsing and monitoring scenario test results. Starts a FastAPI server with Uvicorn.

    How It Works¶

    1. Scans the base path directory for scenario output files (outputs/YYYY-MM-DD/HH-MM-SS/)
    2. Serves a web interface for browsing sessions and viewing individual scenario results, each with its run in an embedded Rerun viewer (Seeing a run in the viewer)
    3. Provides an API for triggering scenario runs and monitoring progress in real time

    Usage¶

    # Start with default settings (127.0.0.1:9000, current directory)
uv run viewer

# Custom host and port
uv run viewer --host 127.0.0.1 --port 8080

# Scan another project: the directory containing outputs/ and multirun/
uv run viewer --base-path /path/to/project

# All options
uv run viewer --help

    Then open http://localhost:9000 (or the configured host/port) in a browser.

    Option Environment variable Default
    --host VIEWER_HOST 127.0.0.1
    --port VIEWER_PORT 9000
    --base-path VIEWER_BASE_PATH the working directory
    --fetch-rerun-web-viewer [--from TGZ] [--version V] — fetch the Rerun web viewer and exit (below)

    Each option defaults to its environment variable, so a flag on the command line wins over the environment. An unknown option is an error (exit 2) and serves nothing.

    The viewer listens on this machine only by default

    The viewer has no authentication, and its API starts scenario runs (POST /api/run) and SLURM submissions (/api/slurm/...). It therefore binds 127.0.0.1 unless told otherwise. It used to bind 0.0.0.0, every interface; to serve other machines as before, pass --host 0.0.0.0 (or set VIEWER_HOST=0.0.0.0) on a network you trust. The viewer prints a warning when it listens on anything but a loopback address.

    Seeing a run in the viewer¶

    A scenario's page shows its run in Rerun's web viewer, embedded in the page: the case's trajectory log made into a Rerun recording (Seeing a run). A recording already beside the log (X.rrd beside X.trajectory.jsonl) is shown as it is; otherwise the viewer makes it the first time the page is opened (in a worker thread, some tens of milliseconds for a case) and keeps it beside the log, or, where the session's directory cannot be written, in its cache directory. A recording beside the log that is older than the log (after a copy that does not keep file times, cp -r, scp, rsync -r) is made again into the cache directory, never over the one beside the log, which may hold the run's sensors. Making one needs the converter in the viewer's environment:

    pip install 'autoware-carla-scenario[rerun]'    # or: pip install autoware-carla-scenario-rerun

    Without it the page says so, and still shows a recording already made. The page's Download .rrd link is the recording itself, for the native viewer (rerun X.rrd).

    The web viewer is the @rerun-io/web-viewer package of the version the converter writes recordings with (RERUN_VERSION, 0.38.1 for converter 0.1; a recording opens only in a viewer of its minor version). By default the page loads it from the unpkg CDN, pinned to that version. For a machine without the network, keep a copy that the viewer serves itself:

    uv run viewer --fetch-rerun-web-viewer                 # from the npm registry, checked against its integrity hash
uv run viewer --fetch-rerun-web-viewer --from web-viewer-0.38.1.tgz   # from the package's tarball, copied in

    The copy goes to ~/.cache/autoware_carla_scenario/viewer/rerun-web-viewer/<version>/ (VIEWER_CACHE_DIR moves the cache) and is used from then on. VIEWER_RERUN_WEB_VIEWER overrides where the viewer comes from: an unpacked copy of the package (a directory), a mirror of it (a URL), or none for no embedded viewer (the page then names the recording only).

    Results on the ODD¶

    A session's page links its results on the ODD (/session/{type}/{date}/{time}/odd): openodd's coverage matrix (openodd.CoverageView) of the cases' coverage files ({stem}_coverage.json), along two ODD attributes picked above it (by default the two the cases were drawn over that tell them apart most). Each cell holds the runs that spent time in it, coloured by what they did -- green passed, red failed, yellow flaky (both), white not sampled -- and a click on one drills into it: the matrix of the next two attributes inside it, and below, the cases in it, each linking to its page (and its run in the Rerun viewer) with its verdict, the buckets it was drawn in and a few metrics of how the ego drove, read off its trajectory log: the least gap from its box to another road user's (min gap), its hardest braking (over half a second), when it first stopped, how far it drove, its top and final speed, and the elapsed time. openodd's plot of the drawn cases (openodd.CasePlot) is shown too.

    Comparing runs¶

    /compare (the navigation bar's Compare, or Compare with past runs on a session's page) compares two or more sessions of the same scenarios (?s=batch/2026-10-18/16-09-52&s=...), the oldest the baseline:

    • Cases are matched by what they ran -- their sweep overrides (less ++odd_case, which names a case's position), else the ODD values they were drawn at -- not by their index, so a case keeps its match when a sweep's order or size changes. Each is marked by how its verdict changed between the first session that ran it and the last: pass → fail (a regression, listed first and in red), fail → pass, flaky, the same, or run by one session only. Beside it, the change of each metric (bold when more than 5%), each run's verdict linking to its page, and side by side: the first and last runs in two Rerun viewers on one page (/compare/runs?run=type/date/time/index&run=...).
    • ODD cells: each session's passes and runs in each cell of the two attributes picked (the buckets the cases were drawn in), red where the last session passes fewer of them, green where more; and openodd's matrix of each session beside the others.
    • Pass rates of each session.

    Running through SLURM¶

    The Run Scenarios panel's Launcher runs the batch here, case after case (local, the default), or submits it as a SLURM array job (SLURM, Running a Batch on SLURM) with the launcher.* keys the panel sets: the partition (from sinfo), array_parallelism, cases_per_task, time, mem, gres, start_stagger_seconds, extra environment variables (launcher.env), and for a viewer whose host sees the nodes' file system at another path (an sshfs or NFS mount) remote_cwd, python and the setup lines a job runs first (A submit host with other paths); the extra overrides can set any other. The viewer runs scenario [--multirun] scenario=... launcher=slurm ... --no-wait (with a sweeper, every case of the sweep) in its base path, and opens the batch's page once it is submitted. Where sbatch is not on the viewer's PATH the option is disabled, and says so.

    A SLURM batch's page (outputs/<date>/<time>/ with a slurm/ directory, whoever submitted it) follows it through squeue and the records its tasks write: each case passed, failed, errored, running, pending or missing (with why: its task's state and error), each submission's job and tasks (state, host, cases done, peak memory), and the cases as they land, before the batch has a summary. Its buttons run scenario-slurm on the batch: Resubmit missing (the cases with no outcome, or that errored), Resubmit failed too (--failed), with the array parallelism and cases per task to use, Collect (the summary and batch_results.json) and Cancel jobs.

    VIEWER_SCENARIO_COMMAND replaces uv run scenario as the command a SLURM batch is submitted with (.venv/bin/scenario, say, where uv run must not sync the environment).

    Web UI Pages¶

    Route Description
    / Session list — displays all test sessions grouped by date/time
    /session/{type}/{date}/{time} Session detail — shows all scenarios in a session with pass/fail status
    /session/{type}/{date}/{time}/{index} Scenario detail — the run in the Rerun viewer, condition tree, per-condition status

    REST API Endpoints¶

    The viewer also provides API endpoints for programmatic use and the web UI's interactive features:

    Method Endpoint Description
    POST /api/refresh Clear result cache and return updated session table HTML
    GET /api/scenarios List all available scenario config names
    POST /api/run/preview Preview the CLI command that would be executed
    POST /api/run Start a scenario execution in the background (409 {"status": "busy"} while a local run is still in progress)
    GET /api/run/status Get current run status (non-streaming)
    GET /api/run/progress SSE (Server-Sent Events) stream for real-time progress
    GET /api/launchers The launchers a run can use here (slurm only where sbatch is, with the partitions)
    GET /api/slurm/submission The batch the viewer last submitted through SLURM, and its page once submitted
    GET /api/slurm/{date}/{time}/status A SLURM batch's cases, jobs and tasks
    POST /api/slurm/{date}/{time}/{resubmit,collect,cancel} scenario-slurm on the batch (resubmit takes failed, array_parallelism, cases_per_task)
    POST /api/recording/{type}/{date}/{time}/{index} Make the case's Rerun recording if there is none; its URL and path (503 with the install hint without the converter)

    Run request body format:

    {
  "scenario": "*/*",
  "extra_overrides": ["server.host=192.168.1.100"],
  "sweeper": "",
  "launcher": "local"
}

    With "launcher": "slurm", "slurm" holds the launcher.* keys: {"partition": "main", "array_parallelism": 2, "cases_per_task": null, "time": "02:00:00", "mem": "12G", "gres": null, "start_stagger_seconds": 30, "remote_cwd": "workspace/OnePlanner", "python": ".venv/bin/python", "setup": "source ~/env.sh", "env": {"NAME": "value"}} (setup: a shell line per line, without ${...} or a backslash continuing it; env: NAME=value lines, or a mapping, each value exported as written, so without ${...} either -- an OmegaConf interpolation in the override the viewer passes on).

    Progress SSE event format:

    {
  "current": 2,
  "total": 5,
  "scenario_name": "intersection_passing/straight",
  "status": "running"
}

    Where status is one of: "running", "idle", or "done".

    Common Use Cases¶

    Use Case 1: Run a Single Scenario¶

    # Start CARLA server first, then:
uv run scenario scenario=intersection_passing/straight

    Use Case 2: Run All Scenarios for a Map¶

    uv run scenario scenario='*/*' map=nishishinjuku

    Use Case 3: Test on a Remote CARLA Server¶

    uv run scenario scenario=intersection_passing/left_turn \
  server.host=192.168.1.100 server.port=2000

    Use Case 4: Detect Missing 3D Models Before Running Scenarios¶

    # 1. Detect lanelets without ground geometry (from the repository root)
uv run detect-no-3d-model autoware_carla_scenario/src/autoware_carla_scenario/examples/conf/map/nishishinjuku.yaml

# 2. The detected IDs are written to no_3d_model_lanelet_ids in the YAML
# 3. Now run scenarios — sweep will skip these lanelets
uv run scenario scenario='intersection_passing/*' map=nishishinjuku

    Use Case 5: Browse Results in the Web UI¶

    # 1. Run scenarios
uv run scenario scenario='*/*'

# 2. Launch the viewer from the project directory: it scans outputs/ and
#    multirun/ there (from elsewhere: --base-path <dir containing outputs/>)
uv run viewer

# 3. Open http://localhost:9000 in a browser

    Use Case 6: Resume a Failed Batch¶

    # Original batch run (5 scenarios, stopped at the 4th, e.g. by Ctrl+C)
uv run scenario scenario='intersection_passing/*'

# Resume from the 4th scenario
uv run scenario scenario='intersection_passing/*' --resume-from 4

    Troubleshooting¶

    "Connection refused" or timeout when connecting to CARLA¶

    Cause: CARLA server is not running, or host/port is incorrect.

    Solution: - Verify the CARLA server is started and accessible - Check server.host and server.port overrides match the server - Increase --timeout for detect-no-3d-model

    "batch scenarios must share the same map"¶

    Cause: Glob pattern matched scenarios configured for different maps.

    Solution: - Use map=<name> override to force all scenarios to use the same map - Or narrow the glob pattern to match scenarios for one map only

    Ego vehicle falls through the ground¶

    Cause: The spawn lanelet has no corresponding 3D ground geometry in CARLA.

    Solution: - Run detect-no-3d-model to identify problematic lanelets - Add them to no_3d_model_lanelet_ids in the map config - Increase entity.ground_projection_ray_distance_lower for deeper ray casting - Increase entity.spawn_retry_max_count for more spawn attempts

    Scenario times out unexpectedly¶

    Cause: scenario.timeout_seconds is too short, or the ego vehicle is stuck.

    Solution: - Increase scenario.timeout_seconds - Check ego.initial_speed_kmh — a value of 0.0 requires autopilot to start moving - Enable verbose logging and check condition statuses in the result JSON

    "Unknown scenario name" error¶

    Cause: The scenario.name field in the YAML does not match any registered scenario class.

    Solution: - Supported scenario names: intersection_passing, lane_change, traffic_light_compliance, temporary_stop - Check the name field in your scenario YAML config
